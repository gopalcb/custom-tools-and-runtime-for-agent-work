Agent Messaging as the System's Nervous System

Agent messaging is not just chat between agents. In this system, a message is a small work envelope that routes tool calls, records state, and leaves an inspectable trail.

The compact message queue has a simple job: accept an envelope, persist it, queue it, dispatch it by topic, attach the result, and persist the final state. Tools are called by routing messages.

A Message Is a Work Envelope

The compact MQ server accepts topic, sender, payload, and an optional event_id. The topic is the route. The payload is the argument bag. The sender is the trace. The event id makes the work easy to find again.

The server adds status, timestamp, and result fields. Then it saves the event before processing begins, so the request remains visible even if the worker fails later.

The Flow Is Small on Purpose

A caller posts a message. The server stores it as pending. A worker marks it processing. The handler reads the topic and runs the matching deterministic operation. The result is attached, and the final processed state is written back to disk.

There is no hidden orchestration trick in the middle. The handler is a topic switchboard for routes like read-file, write-file, run-workflow, memory-store, todo, and invoke-function.

How Tool Calls Ride on Messaging

A tool call is just a message whose topic points at a tool-shaped handler.

uses: message
topic: invoke-function
payload:
  name: web-search

The workflow runner can treat this as a message step. The MQ handler receives topic: invoke-function, reads payload.name, and dispatches the allow-listed helper. The same shape works for memory, workflow resolution, file operations, and task creation.

Why This Feels Different From Direct Calls

A direct function call disappears when the process exits unless someone records it. A message creates evidence as part of the call: who asked, which topic handled it, what arguments were supplied, which status it reached, and what result came back.

Two Kinds of Messaging

The compact MQ server is for topic-dispatched runtime work. It stores event snapshots under .agent-state/messages/ and is best for deterministic actions.

The file-backed agent message bus under agent-custom-tools/event-messaging/ is for agent-to-agent inbox behavior. It keeps inbox, processed, failed, records, tasks, threads, and errors visible on disk.

The Handler Is the Boundary

An agent can ask for work before it reaches this layer, but the handler only accepts known topics. Unknown topics fail. File paths stay inside the project root. Memory actions are reduced to store, search, and health. Helper functions are allow-listed.

The Mental Model

Think of the message queue as a small desk in the middle of the runtime. Agents, workflows, and operator surfaces put labeled envelopes on the desk. The worker opens one envelope at a time. The topic tells it which tool shelf to use. The result goes back into the envelope, and the envelope is filed where the operator and future tools can inspect it.
